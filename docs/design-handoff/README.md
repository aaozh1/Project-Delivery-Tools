# Handoff: DPM — Design Project Manager

ระบบภายในสำหรับบริษัทออกแบบสถาปัตยกรรมและตกแต่งภายในในประเทศไทย
ควบคุมโครงการ 4 สายงาน: สถาปัตยกรรม (AR) · ตกแต่งภายใน (ID) · บ้านพักอาศัย (House) · กราฟิก (Graphic)

## Overview

DPM ควบคุมโครงการตั้งแต่ระดับบริษัทลงไปถึงงวดงาน ตามลำดับชั้น
**บริษัท → แผนก → Squad → โครงการ → งวดงาน**

หน่วยวัดงานเดียวของระบบคือ **"คน-สัปดาห์" (person-week)**
1.00 = ทำงานเต็มสัปดาห์ให้โครงการเดียว ป้อนทีละ 0.25
ระบบนี้ **ไม่มีการลงเวลารายชั่วโมงหรือรายวันโดยเจตนา** — หน้า "จัดสรรกำลังคน" เป็นแหล่งข้อมูลเดียวที่ใช้คำนวณต้นทุนค่าแรงจริงของทุกโครงการ ถ้าหน้านั้นกรอกยาก ตัวเลขทั้งระบบจะผิด

กติกาสิทธิ์ที่ต้อง enforce ในทุกหน้า:
- หัวหน้า Squad จัดสรรได้เฉพาะสมาชิกใน Squad ตัวเอง ห้ามข้าม Squad
- เฉพาะหัวหน้าแผนก (HoD) เท่านั้นที่ย้ายคนข้าม Squad ได้
- 1 Squad = 3–6 คน ดูแล 2–4 โครงการ
- ทุกที่ที่ระบบบอกว่า "ทำไม่ได้" **ต้องบอกด้วยว่าต้องทำอย่างไร** และติดต่อใคร

## About the Design Files

ไฟล์ในโฟลเดอร์ `designs/` คือ **design reference ที่เขียนเป็น HTML** — เป็น prototype ที่แสดงหน้าตาและพฤติกรรมที่ต้องการ **ไม่ใช่ production code ที่ก๊อปไปใช้ตรง ๆ**

งานคือ **สร้างหน้าจอเหล่านี้ขึ้นใหม่ใน codebase เป้าหมาย** ด้วย pattern และ library ที่ codebase นั้นใช้อยู่แล้ว (React / Vue / Next.js / อื่น ๆ) ถ้ายังไม่มี codebase ให้เลือก framework ที่เหมาะที่สุดแล้วทำใน environment นั้น

หมายเหตุทางเทคนิคของไฟล์ prototype:
- ทุกไฟล์เป็น `.dc.html` ที่ใช้ runtime เล็ก ๆ (`designs/support.js`) แปลง template + logic class เป็น React ตอนรัน — **runtime นี้ไม่ต้องพอร์ตไปด้วย** ให้อ่านเป็นตัวอย่างเท่านั้น
- template อยู่ในบล็อก `<x-dc>` (markup + inline styles ทั้งหมด) และ logic อยู่ใน `class Component extends DCLogic` ที่มี `renderVals()` คืนค่าที่ template ใช้ → เทียบได้กับ component ที่มี `state` + computed values
- `<sc-for list as>` = `.map()` · `<sc-if value>` = conditional render · `{{ x }}` = ค่าจาก `renderVals()`
- **สไตล์เป็น inline ทั้งหมดโดยเจตนา** ตอน implement ให้ย้ายเป็น token/utility class/styled-component ตามที่ codebase ใช้ อย่าคง inline style ไว้
- `style-hover="…"` ใน template คือ pseudo-state `:hover` (เช่นเดียวกับ `style-active`, `style-focus`)

## Fidelity

**High-fidelity (hifi)** — สี typography ระยะ และ interaction เป็นค่าจริงที่ต้องการทั้งหมด
ให้ recreate ให้ตรง pixel เท่าที่ library ของ codebase เอื้อ โดยใช้ค่า token ในเอกสารนี้และในหน้า `Design System.dc.html`

ทุกหน้าออกแบบที่ความกว้าง **1440px (max-width) padding ซ้ายขวา 32px** ยกเว้น
- `Growth Profile` และ `Design System` ใช้ max-width 1200/1280px
- `Weekly Log` เป็น **mobile-first** (390 × 844) และมีเวอร์ชัน desktop อยู่ในไฟล์เดียวกันเพื่อเทียบ

## Interactions & Behavior

- **Stepper / ช่องจัดสรร**: ปรับทีละ 0.25 เท่านั้น (`Math.round(v*4)/4`) ไม่ต่ำกว่า 0 · ช่องจัดสรรแบบ 4 ก้อน: คลิกก้อนที่ n → n×0.25, คลิกก้อนที่ค่าปัจจุบันซ้ำ → 0
- **การคำนวณต้องสด (synchronous)** ห้ามมีปุ่ม "คำนวณ" ห้าม debounce ที่รู้สึกได้ — ปรับแล้วตัวเลขขยับทันที
- **Feedback ของการคำนวณ**: ป้าย "สด" ↔ "กำลังคำนวณ" + จุดเต้น 2.6s + พื้นกล่องผลลัพธ์เปลี่ยนสั้น ๆ 900ms แล้วจางกลับ (`setTimeout` เดียว ยกเลิกด้วย `clearTimeout` เมื่อมีการเปลี่ยนซ้ำ) · **ห้าม spinner ห้ามตัวเลขวิ่ง**
- **Transition ที่ใช้จริง**: `width 220–300ms ease` (แถบ) · `color 400ms ease` (ตัวเลขที่เพิ่งเปลี่ยน) · `background 700ms ease` (กล่องผลลัพธ์) · `border-color 400ms ease` (กล่องเตือน) · ไม่มี animation อื่นนอกจาก `dpmBreathe` (จุดสด) และ `dpmSkeleton` (โหลด)
- **Hover**: พื้นแถวตาราง → `#FAFAF8` · พื้นเมนูบนพื้นรอง → `#E8E7E2` · ปุ่มหลัก `#2B4C7E` → `#1C1C1A` · ปุ่มรอง เส้น `#E3E2DD` → `#1C1C1A` **ห้ามใช้เงาหรือการขยับตำแหน่งเป็น hover effect**
- **พับ/ขยาย**: การ์ดงวด (1 ที่ขยายได้ทีละอัน) · กลุ่ม Squad (พับได้อิสระ) · การ์ดโครงการในบันทึกรายสัปดาห์ · การ์ดที่พับต้องยังบอกข้อมูลพอ (ชื่อ % จำนวนเงิน) โดยไม่ต้องขยาย
- **Dirty state (Admin Console)**: เทียบทุกค่ากับค่าที่บันทึกไว้ · แถบล่างเปลี่ยนเป็นเหลืองพร้อมนับจำนวนค่าที่แก้ · กดบันทึกเปิด modal ที่คำนวณผลกระทบจากข้อมูลจริง ไม่ใช่ข้อความคงที่
- **Loading**: skeleton บล็อกสี `#F2F1ED` `animation: dpmSkeleton 1.4s ease-in-out infinite` (opacity 0.5→1) ปุ่มคงความกว้างเดิมไม่กระโดด
- **Error**: กรอบและตัวอักษร `#B33A3A` + พื้น `#FBF1F1` **ต้องบอกด้วยว่าต้องแก้เป็นเท่าไร** (เช่น "เกินเต็มสัปดาห์ — ลดลง 0.25")
- **Empty**: ข้อความสีจาง + ลิงก์ทางออกทันที (เช่น "ยังไม่มีการจัดสรร / จัดสรรกำลังคน") ห้ามปล่อยช่องว่างเปล่า
- **ไม่มีสิทธิ์เข้าถึง — ต้องไม่ดูเหมือน error** ทำ 3 ระดับ (ดู Design System): ระดับช่อง (`••••••` + ปุ่มเปิดดู + แจ้งว่าบันทึก Audit Log) · ระดับบล็อก (พื้น `#F2F1ED` ไอคอนล็อกเทา + เหตุผล + ปุ่ม `ขอสิทธิ์เข้าถึง` + ระบุตำแหน่งคนที่ติดต่อ) · ระดับปุ่ม (ปุ่มเทา `cursor:not-allowed` + คำอธิบายกติกา + ลิงก์ทางออก)
  **กติกาการเขียน:** ใช้พื้นเทากลางและตัวอักษรสีปกติ ไม่ใช้แดง · ห้ามใช้คำว่า "ผิดพลาด" "ไม่ได้รับอนุญาต" "Forbidden" · ต้องระบุ**ตำแหน่ง**ของคนที่ติดต่อได้ ไม่ใช่แค่ "ผู้ดูแลระบบ"
- **Responsive**: หน้าผู้จัดการทั้งหมดออกแบบสำหรับเดสก์ท็อป (max-width 1440px) ตารางกว้างให้ scroll แนวนอนได้แต่ห้ามให้คอลัมน์ยุบจนคำตกบรรทัด — ใช้ grid ที่มีความกว้างคงที่ตามที่ระบุในแต่ละหน้า + `white-space:nowrap` กับ label ภาษาไทย และ `overflow:hidden; text-overflow:ellipsis` กับชื่อโครงการ · หน้าบันทึกรายสัปดาห์เป็น mobile-first

### รูปแบบจำนวนเงินและตัวเลข
- จำนวนเต็มในตารางที่ต้องบวกเลขด้วยตา: `฿1,800,000`
- ค่าใช้จ่าย: `−฿842,000` ใช้ **− (ขีดยาว) นำหน้า ไม่ใช้วงเล็บ** และไม่ใส่สีแดงถ้าเป็นรายการปกติ
- ตัวเลขระดับผู้บริหาร: ย่อ `฿48.2M` (ทศนิยม 1 ตำแหน่ง) · พื้นที่จำกัด: `฿842K`
- เปอร์เซ็นต์ติดลบที่เป็นปัญหาจริง: `−4%` สีแดง · **ห้ามผสม ฿ กับ %**
- ยังไม่มีข้อมูล: `฿0` สีจาง ห้ามแสดงช่องว่างเปล่า
- คน-สัปดาห์: ทศนิยม 2 ตำแหน่งเสมอ `0.50` `1.25` (ยกเว้นตัวเลขรวมระดับสรุปที่ใช้ `44`)

### สัญลักษณ์สถานะ (บังคับใช้คู่กับสีทุกครั้ง)
`▲` วิกฤต · `◆` เตือน · `●` ปกติ · `○` โหลดต่ำ/ยังไม่เริ่ม · `✓` ผ่าน/อนุมัติ/ทำแล้ว · `◐` เคย/กำลังทำ · `◑` ส่งลูกค้าแล้ว
**เหตุผล: ผู้ชายไทยราว 8% ตาบอดสี — ทุกสถานะต้องอ่านได้จากรูปสัญลักษณ์และคำ ไม่ใช่จากสีอย่างเดียว และต้องอ่านได้เมื่อพิมพ์ขาวดำ**

### สถานะงวดงาน 6 ขั้น (เดินหน้าทางเดียว)
`ยังไม่เริ่ม` ○ ขาวกรอบประ → `กำลังทำ` ◐ พื้น `#F2F1ED` → `ส่งลูกค้าแล้ว` ◑ ขาวกรอบดำ → `อนุมัติแล้ว` ✓ พื้นดำ → `วางบิลแล้ว` ✓ พื้น `#2B4C7E` → `รับเงินแล้ว` ✓ พื้น `#2F7A4F`
มีสองรูปแบบ: ป้ายเดี่ยวสำหรับใช้ในตาราง และแถบเส้นทาง 6 ช่องสำหรับหน้ารายละเอียดงวด

## หลักการที่ต้องคงไว้ตอน implement

1. **อารมณ์แบบสตูดิโอสถาปัตยกรรม** — สงบ แม่นยำ มีระเบียบ ไม่ใช่ SaaS สีจัด ไม่ใช่ fintech dashboard · ผู้ใช้คือดีไซเนอร์ เครื่องมือต้องดูเหมือนสิ่งที่ดีไซเนอร์เคารพ
2. **ใช้เส้นบาง 1px แทนเงาทุกกรณี** — การเน้นระดับสูงสุดคือเปลี่ยนสีเส้นเป็น `#1C1C1A` (ใช้ได้กล่องเดียวต่อหน้า)
3. **ผู้บริหารต้องอ่านตัวเลขสำคัญได้จากระยะ 2 เมตร** — KPI ไม่ต่ำกว่า 34px, Margin 40px
4. **สถานะต้องมีทั้งสีและสัญลักษณ์** ทุกที่ ไม่มีข้อยกเว้น
5. **ทุกที่ที่บอกว่า "ทำไม่ได้" ต้องบอกด้วยว่า "ต้องทำอย่างไร"** และติดต่อใคร (ตำแหน่ง ไม่ใช่ "ผู้ดูแลระบบ")
6. **ภาษาไทยทั้งหมด คำต้องไม่ล้นกล่อง** — label ภาษาไทยต้อง `nowrap` + กว้างพอ, ชื่อยาวใช้ ellipsis, ห้ามให้แถวสูงไม่เท่ากันเพราะคำตกบรรทัด
7. **กติกา Squad เป็นเรื่องของสิทธิ์ ไม่ใช่ข้อความเตือน** — ต้อง enforce ที่ backend ด้วย และทุกจุดที่ติดกติกาต้องมีเส้นทางส่งคำขอถึงหัวหน้าแผนก
